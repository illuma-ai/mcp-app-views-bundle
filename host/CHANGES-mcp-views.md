## CH-219 — MCP App tool calls honour the tool-approval policy (flag-gated)
- status: done
- why: an app view asking to run a tool on its own server always raised the "Run tool from app?" dialog, even for tools the administrator already allows or the agent already has on Always-approve, so a view felt unlike the real app
- approach: new flag `mcpSettings.appsHonorToolApproval` (default off, today's behaviour). On, the server decides from the existing tool-approval policy (single source: the agent runtime's predicates in packages/api/src/agents/hitl): an admin deny rule blocks the call (403 with a clear message, enforced on the call route whatever the client does); an admin allow rule, or the conversation's agent holding the tool in Always-approve mode with no admin ask rule matching (and `agentModes` on), lets it run without the dialog; ask rules, unmatched tools (modes default and dontAsk) and app messages keep the dialog. Ask rules win over allow; deny wins over everything. The client asks the same call route with `verdictOnly` before it shows the dialog, so no policy matching lives on the client; any fault answers ask. The startup config publishes the flag only when on

## CH-221 — no hard context-limit stop; tool results capped; PTC policy bypass closed
- status: done
- why: the owner requires that a person never meets a hard "context limit exceeded" stop; the agent runtime compacts and retries at most twice and then the turn ended in an error card. Separately, an administrator deny/ask rule was bypassed when a tool ran from code (programmatic tool calling)
- approach: (1) last resort in the host: on an overflow the runtime gave up on, the largest tool results in the prompt are replaced with `result removed: N chars, re-run the tool with a narrower query` and the run retried, twice more (attempt 1 the largest result, attempt 2 the larger half of those left), so four tries in all with the runtime's own two; the error shows only after the last. The runtime's own attempt cap is fixed inside the runtime and not configurable from the host, so the extra attempts are made by the host around the whole run (the existing run wrapper in turnFallbackText.js). The error card for `final_context_overflow` and `empty_messages` gets a "Compact and retry" button: it compacts the conversation, then resends the failed message from the summary boundary. (2) `endpoints.all.maxToolResultChars: 60000` in the host config (the key initialize.ts reads when the endpoint has none), documented in docs/mcp-ui/CONFIG.md, fragment regenerated. (3) a tool call with no tool-call id (from code) is now checked against the administrator allow/ask/deny rules: deny refuses, ask refuses with "needs approval"; the `test.failing` cases became ordinary tests. (4) tool definitions over the window: when the definitions of the tools an agent carries would take more than 40% of the context window (live case: 64 tools, ~156k tokens of schema against a 129k window, so no message fit and Compact could not help), `initializeAgent` defers the MCP tools beyond that budget (`defer_loading`; explicitly attached first, then most recently used when a recency list is supplied, then original order), adds the tool search definition, and appends one line to the agent's additional instructions that more tools load on demand; the turn never fails on tool size. The deferral runs on every request, so "Compact and retry" (a new request) gets it too. Only MCP tools are deferred and only when the `deferred_tools` capability is on. (5) audit fix: the fork-overlay audit read a CRLF working tree as wholly changed whenever git ran without the system `core.autocrlf=true`; `git()` now pins `core.autocrlf=input`
